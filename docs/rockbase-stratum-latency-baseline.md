# Rockbase 矿池 Stratum 延迟基线

> 本文档记录 Rockbase 矿池（ckpool）在 **SDIO WiFi 与 USB 有线** 两种网络模式下 18 台矿机的 share 上报延迟基线及对比。
> 核心诉求：18 台矿机 share 延迟 ~200ms 对局域网不可接受，需定位根因（矿机端 WiFi vs 板子压力）。

## 测试环境

| 项 | 值 |
|----|----|
| 测试板 | `192.168.124.15`（1G 版，mmc0=SDIO WiFi, mmc1=SD card） |
| 内核 | 6.6.36 (`#2 SMP Thu Aug 20 15:03:53 CST 2026`) |
| 网络模式 | `sdio_wifi`（`/tmp/rockbase-net-mode`），接口 `wlan0`，驱动 `rtl8189fs` |
| 无有线网卡 | 板子仅 `wlan0`/`wlan1`，`lsusb` 仅见 dwc2 OTG 控制器，无 USB 网卡 |
| 矿机连接数 | **18 台**（`netstat` 统计 `:3333` ESTABLISHED） |
| 矿机分属用户 | 2 个（ckpool `pool.status`: Users=2, Workers=18） |
| 开机时长 | ~5h17m，load average 2.15 |

## 实测数据（2026-08-21）

### 1. WiFi 链路质量

| 项 | 值 |
|----|----|
| 信号强度 | **-58 dBm** |
| 连接速率 | **72.2 Mb/s**（2.4G，20MHz 单流上限） |
| Link Quality | 52/70 |

### 2. 网络延迟（ping RTT）

| 目标 | min | avg | max | 判定 |
|------|-----|-----|-----|------|
| 网关 AP (192.168.124.1) | 1.740ms | **17.798ms** | 56.663ms | 板子→AP 正常 |
| 矿机 .10 | 40.972ms | **286.191ms** | 1068.321ms | 极慢，抖动剧烈 |
| 矿机 .14 | 74.435ms | **227.852ms** | 524.408ms | 极慢 |
| 矿机 .88 | 28.281ms | **184.782ms** | 662.046ms | 极慢 |
| 矿机 .99 | 70.255ms | **221.246ms** | 550.834ms | 极慢 |

**关键现象**：ping 网关仅 ~18ms，ping 矿机却 184~286ms，说明瓶颈在「板子↔矿机」的双向空中链路，而非板子到 AP 的上行。

### 3. 矿机硬件组成

**18 台矿机均为「ESP32 控制 + ASIC 算力」矿机**：ESP32（`ac:a7:04` 前缀）只负责 WiFi 联网、控制与 share 上报，真正算力来自 ASIC 芯片。挖矿算力本身不耗板子资源，但 share 上报走 ESP32 的 WiFi 有固有延迟。

ckpool worker 名揭示的矿机型号构成：

| 型号 | 台数 | 单台算力 | 说明 |
|------|------|---------|------|
| NMQAxe++ | 14 | 4.2~7.1T | 主流量产机型 |
| bm1373x4 | 1 | 9.48T | Bitmain BM1373 ASIC |
| bm1373x2 | 1 | 10.3T | Bitmain BM1373 ASIC |
| NMAxe | 1 | 502G | 低算力 |
| NMAxeGamma | 1 | 953G | 低算力 |

| MAC 前缀 | 厂商 | 台数 | 角色 |
|----------|------|------|------|
| `ac:a7:04` | Espressif ESP32 | 16 台 | 控制/WiFi/上报 |
| `10:20:ba` | 其他（.88/.99，即 2 台 bm1373） | 2 台 | 控制/WiFi/上报 |

> 修正：早期误判「18 台全是 ESP32 低端芯片挖矿」。实际是 ASIC 矿机，ESP32 仅控制面。`.88/.99`（`10:20:ba`）对应 2 台 bm1373，延迟特别高（见有线对比）。

### 4. 8189fs SDIO 卡顿（叠加因素）

`dmesg` 中 `[rb8189-diag]` 日志的 SDIO 读延迟采样（`elapsed_ms`）：

```
elapsed_ms=1276, 1288, 32, 188, 28, 88, 36, 88, 28, 184
```

峰值 **1276ms**，说明板子 WiFi 驱动本身仍在卡顿（即 freeze 调试对象），卡顿时所有 WiFi 流量（含 share 收发）被阻塞。

### 5. ckpool 池状态

```json
{"Users":2,"Workers":18,"Idle":0,"Disconnected":2}
{"hashrate1m":"87.3T","hashrate5m":"88.3T","hashrate15m":"88.5T","hashrate1hr":"88.3T"}
{"accepted":994793503,"rejected":529084,"SPS1m":5.0,"SPS5m":5.0,"SPS15m":5.0}
```

- 总哈希率 87.3 TH/s，SPS ~5.0
- 18 台矿机 TCP 连接 Recv-Q 大多为 0，仅 .111 有 39 字节积压（偶发）

## 根因结论（WiFi 模式，三层叠加）

1. **WiFi 半双工共享介质（主因）**：板子 + 18 台矿机 = 19 个 WiFi 客户端挤同一 2.4G AP，空中时间片竞争导致延迟高、抖动大。
2. **矿机端 ESP32 控制面处理慢**：share 上报走 ESP32 的 WiFi + 控制处理，固有延迟，板子侧无法优化。
3. **8189fs SDIO 卡顿放大**：板子 WiFi 驱动 SDIO 读延迟峰值 1276ms，卡顿时阻塞全部 WiFi 流量。

## 有线实测对比（2026-08-21，板子 124.30）

切换有线后板子为 `192.168.124.30`（1G，`usb_eth`，r8152 千兆 USB 网卡，接口 `eth0`）。

| 指标 | WiFi（124.15） | 有线（124.30） | 结论 |
|------|----------------|----------------|------|
| 网络模式 | sdio_wifi (8189fs) | usb_eth (r8152) | ✅ 已改 |
| ping 网关 | 17.8ms | **0.8ms** | ✅ 板子侧改善 20× |
| ping 矿机 .10 | 286ms | 227ms | ❌ 几乎无改善 |
| ping 矿机 .14 | 227ms | 158ms | ❌ 无改善 |
| ping 矿机 .88 | 184ms | **953ms** | ❌ 更差 |
| ping 矿机 .99 | 221ms | **1363ms** | ❌ 更差 |
| Workers / 算力 | 18 / 87.3T | 18 / 90.9T | 持平 |
| SPS | 5.0 | 6.0 | 持平 |

**结论**：改有线后板子侧（8189fs SDIO 卡顿 + 板子上行 WiFi 半双工）已彻底消除，网关延迟 17.8ms → 0.8ms。但矿机端延迟几乎不变，`.88/.99`（bm1373）反而更差。说明 **share 延迟的主因在矿机端 WiFi 链路，不在板子侧**。

## 板子压力 vs 矿机端归因（2026-08-21）

**问题**：share 延迟高是否因为 k230 板子压力大？

### 板子真实压力（124.30，单核 RISC-V）

| 指标 | 实测值 |
|------|--------|
| CPU 核数 | **1 核** |
| 瞬时 CPU | usr 26% + **sys 52%** + idle 21% |
| loadavg | 2.62（运行队列 2/152） |
| 内存 | free 13M / available 245M，无 swap |

sys 52% 构成：**kswapd 内存回收**（`pgscan_kswapd=431万页`）+ **r8152 USB 网卡中断**（IRQ 85 `dwc2_hsotg` 累计 3800 万次）+ TASKLET 98.6万 + RCU 338万。bitcoind ~6%，**ckpool 仅 ~0.7%**。

### 三条铁证：板子压力不是主因

1. **ckpool 几乎空闲**：3 秒仅 2 个 CPU ticks（~0.7%）。若板子 CPU 抢占导致 share 延迟，ckpool 应高 CPU 排队等待，实际闲得很——share 处理极轻量且未等调度。
2. **ping 网关 0.8ms**：ICMP 走完整路径「USB 网卡中断 → 软中断 → netfilter → socket → 回包」仅 0.8ms，证明板子网络栈 + 中断处理完全正常，sys 52% 没把网络压慢。
3. **无 D 状态进程**：无进程卡不可中断睡眠（IO 等待），内存回收未造成 IO 阻塞。

### 延迟构成定位

```
share 延迟 ≈ 网络 RTT（矿机端）
           = ping 矿机 158~1363ms（纯 ICMP，已不含 share 处理）
板子侧贡献 < 5ms（ckpool 验证 + 网络栈，ping 网关 0.8ms 佐证）
```

`ping 矿机` 是纯 ICMP RTT，尚未到 share 处理层就已 200ms 量级 → 延迟几乎全在矿机端（WiFi 半双工 + ESP32 控制面处理慢）。

### 保留项

板子 sys 52%（kswapd 回收）+ 单核是**真实隐患**，虽非本次 200ms 主因，但内存回收风暴 + USB 中断洪峰同时发生时会造成瞬时延迟尖峰（部分解释 1068ms/1363ms 毛刺），与矿机端 WiFi 重传叠加。内存紧张是独立问题，需另案处理。

## 最终结论

- **share 延迟 200ms 主因 = 矿机端 WiFi 链路**（半双工 + ESP32 控制面），板子改有线只消除自身侧，矿机端不动则延迟不降。
- **板子压力（单核 78% 忙、kswapd 回收）是次要因素**，贡献 < 5ms，但属独立隐患。
- **根治方向**：矿机端改有线接入，或优化矿机 share 上报频率/批处理；板子内存紧张另案处理。

## 对比指引（改有线后复测）

切换有线后，用相同命令复测以下指标，与上表对照：

```bash
# 1. 确认网络模式已切换
cat /tmp/rockbase-net-mode          # 期望 NET_MODE=usb_eth

# 2. 矿机连接数

# 3. 延迟（重点看 ping 矿机）

```

## 排查经验

- **延迟定位手法**：`ping 网关` vs `ping 矿机` 对比——网关快、矿机慢 → 瓶颈在客户端空中链路，而非服务器上行。
- **矿机芯片识别**：`ip neigh show` 看 MAC 前缀，`ac:a7:04` = Espressif ESP32（矿机控制面）。
- **真实矿机型号识别**：看 ckpool worker 名后缀（如 `bm1373x4` = Bitmain BM1373 ASIC），比 MAC 前缀更能反映算力芯片。
- **板子网络接口确认**：`cat /sys/class/net/*/device/uevent` 看 `rtl8189fs`（WiFi）或 `r8152`（有线），`lsusb` 见 `dwc2_hsotg` OTG 控制器。
- **板子压力 vs 矿机延迟判别**：`ping 网关` 快（<5ms）+ ckpool 低 CPU → 板子不是瓶颈；`ping 矿机` 慢才是真瓶颈，在矿机端链路。
